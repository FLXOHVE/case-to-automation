# 从用例实现到执行验证

## 先落实项目结构和能力复用

以[项目适配](project-adapter.md)中已核对的当前模块约定组织脚本；先选有效的同类测试作为结构依据，
再填入源用例的业务步骤，不把其他项目的目录、装饰器、基类或报告机制搬进来。
测试层编排业务步骤，沿项目原有分层调用；已有连接、fixture、页面对象、断言和恢复能力直接使用，
不在用例中复制底层连接、选择器、协议或等待实现。临时调查脚本不能代替最终的原生用例接入。

已有能力完全匹配时直接调用；只有部分缺口时优先在现有职责层最小扩展并检查已有调用方，
确无匹配能力才新增。对新增文件、类和方法逐项说明必要性；没有新契约的改名副本或纯转发包装应去掉。
语义不匹配的能力不能为追求复用而硬套；有依据的修复需验证受影响的既有调用，不扩大无关改动。

## 建立逐步对应

开始实现前，把每条用例的源ID/步骤、前置、操作、预期和清理，与真实能力及证据来源对应。
动作和判据分别核对：输入参数写进客户端变量后再读该变量，只证明客户端保存过参数。
用例要求的业务结果应通过目标系统的状态、页面、响应、存储或相应物理观测确认。

前置分开记录源用例规定的业务起点与实际接口需要的连接/登录/页面就绪条件。
只要求修改保存且未规定初态时读取本次初值，不擅自假定默认Off；要求Off→On时先记录原值，再建立并确认Off。
把本次将改变的配置、创建对象和页面/会话位置列成恢复清单，在首个副作用前安装恢复。
检查项目公共生命周期的额外动作，防止窄范围测试结束时发生未经本次范围支持的关机/解绑/数据清空。

缺少判据时记录具体缺口，不通过缩小原预期、改成功文案或扩大超时迁就产品现状。
一个用例由多个脚本组合时列明各自覆盖的步骤及组合条件；共享前置和重复轮数不算新增覆盖。

## 缺少能力时开发什么

| 缺口 | 调查及实现 |
| --- | --- |
| 页面操作 | 当前版本页面/控件树、已有页面对象、可见/可点/无遮挡目标；无导航时按[页面调查](navigation-discovery.md)建立路径；补业务方法，避免依赖另一项目坐标 |
| 协议/接口动作 | 版本匹配的协议/API及产品处理入口，核对ID、长度、编码、单位、校验、错误语义和业务完成条件 |
| 结果回读 | 补独立状态查询/订阅/页面读取，区分缓存、旧响应、错对象、无响应和真实未生效 |
| 清理 | 按本次创建的唯一对象或原状态恢复；提前注册，覆盖前置做一半失败，不删除无关数据 |
| 执行基础 | 沿用项目栈补最小配置、发现、精确选择及原生报告；不另建庞大执行平台 |

控制、读取/解析、断言、测试编排各放项目适当层。外部资料仅作为证据，不能授权修改产品或操作另一环境。
需要改产品增加测试入口时，明确这是额外产品改动；不能用直改内部状态代替受测业务操作。

新协议/解析可用版本匹配的固定样本做独立验证，避免用被测编码器自产的结果作为唯一预期。
新控件定位检查重复文本、隐藏和遮挡；新状态等待检查旧值已等于期望、结果未变化和超时。
有限重试适用于已知幂等读/写；创建、toggle等结果未知时先查询核实，不重复发送。

## 跨系统事件链

对用例涉及的每个事件分别对应：来源系统和真实入口、操作主体及权限、关联标识、预期状态转换和独立回读。
上游创建/批准/支付/绑定等动作与下游接收通知分别验证，不能因为通知接口可调就认为上游业务已实现。
身份/站点、事件ID或业务字段只有在契约与实际回读有依据时才使用，不生成看似合理的来源数据补空白。

复用项目已有客户端、受控夹具、凭证回读、写入日志和资源锁。接口文档、私有配置路径或本地执行开关
都不授予服务器权限；缺操作权限或来源契约时明确阻塞该步骤，继续独立且已具备条件的部分。
没有用户授权时不扩大账号权限、变更业务配置或调用另一个高权限入口代替原用例。

报告区分真实端到端、开发/管理夹具集成、模拟事件接收和接口部分验证。比如模拟支付回调能验证接收后的处理，
不能证明真实付款；直接发放奖励不能证明推荐/试驾/问卷来源事件已正确触发。合法夹具可以使用，但保留其边界。
跨系统写入结果不明时保留原始事件、操作日志及核对状态，按项目规则停写；不换账号、换单或重放请求绕过未知结果。

## 验证顺序和结果

先对照实际项目约定核对目录/声明、注册发现、生命周期和分层调用，使用现有格式/类型/静态检查入口，
审阅新增实现是否与公共能力重复；再核对接口及关联，跑与改动有关的离线检查，随后在明确授权的目标环境精确执行。
发现/注册验证应使用项目真实入口及精确选择规则，并核对用例ID和参数变体；能单独运行不等于已被项目接入。
只选与当前改动和未决风险有关的检查；通过后只有新改动、失败或未决问题才扩大或重复检查。
普通编排不机械增加mock测试；涉及解析、状态、恢复或新基础工具时检查有意义的失败分支。

检查原生运行器真实执行了预定测试，有对应的业务断言，实际依赖启用，前置、正文和关键清理错误均进入最终结果。
测试发现、进程成功退出、接口成功、截图存在以及原生报告里的零失败，均需结合测试数量、选择和跳过情况判断。
分别统计源用例、参数变体、执行次数和报告记录；例如pytest可能为同一测试的正文失败与teardown错误各写一条JUnit记录，
不能据此算作两条业务用例或新增覆盖。

可生成JUnit XML的项目可使用`../scripts/run_and_verify.py`。先查看脚本`--help`，提供已核对的原生命令，
选择本次测试及相关改动能力/配置源文件、期望数量和全部原生测试标识；不把示例命令直接当成目标项目命令。
辅助脚本创建新的运行目录，记录命令和源码哈希，验证本次JUnit；若项目不能输出JUnit，使用原生结果做同等核对。
同时核对套件级初始化/清理错误和未知结果标记；报告不完整或格式无法可靠识别时保留未通过，调查原生结果后再适配。
不执行无法识别的静默成功、仅模拟驱动路径或绕开清理的流程来宣称目标环境通过。

## 失败和修复边界

- 脚本/封装错误：用失败证据定位，修复后对相关范围复测，记录代码和运行变化。
- 产品不符：保留期望、实际及证据，不改预期或删断言求通过。
- 环境问题：记录实际缺失的连接、身份、服务、资源或依赖；恢复必要条件后再执行，不误报产品功能失败。
- 尚无法定位：保留未知状态和最小后续调查项；不要把所有异常归给网络或默认当作脚本问题。

超时/中断后可能仍有外部操作或进程，按项目恢复规则核实现场，不能仅因测试进程结束就重放动作。
关键清理失败保留为未通过；同时保留正文原始错误。失败回合及后续修复不能被最终一次通过覆盖。

独立性验证关注单条起点、反向起点、复跑和与相邻用例组合后的状态污染。
稳定性按明确环境、轮数、顺序、失败和未执行统计表达；没有统一的“三次通过就稳定”阈值。

## 交付

分别列出复用和新增能力、源码位置及依据、关联源用例和覆盖预期、静态/离线/目标环境的实际检查，
以及目标身份/版本、原生测试ID、实际数量、run目录、日志/报告、清理结果和未覆盖项。
缺环境时明确停在哪个验证阶段；只交付实际完成结果，不把“流程写进skill”当作脚本运行证据。
